# Manipulation core — scope & phased plan

> **Status: M1 + M2 + M3 + M4 in the tree; M5 plan.** M1's wrist force/torque sensor, M2's
> force-regulated insertion, M3's Cartesian admittance (compliant) control and M4's actuated
> gripper (grasp-force control + a friction grasp + a grasp-slip curve + a weld-free
> grasp-and-carry on the arm, now also driving **both hands** of the live S0–S7
> demonstrator cycle on an opt-in scene that has no `weld` left in it) are all
> implemented and tested; only M5, the
> hardware bring-up, is plan (see the status of each below). This scopes how
> SkateArm's manipulation evolves from the original
> *scripted position control + joint-torque watchdog + weld-constraint grasp* into genuine
> **contact-force manipulation** — wrist force/torque sensing, force-regulated and compliant
> control, and a real grasp — sim-first and honest about the hardware boundary. It exists
> because the portfolio review correctly flagged the manipulation core as the project's single
> largest remaining gap.

## 1 · Where we are today (grounded in the code)

*This section is the **pre-M1 baseline** — the state that motivated the plan, kept as written so the gap it describes stays legible. M1–M4 below have since shipped and supersede the "Force sensing" and "Compliance" rows in particular; read §3 for what the tree does today.*

| Concern | Today | Verdict |
|---|---|---|
| Arm control | MuJoCo `position` servos (kp = 100, joint damping 2.0, armature 0.05); DLS-IK to Cartesian targets; gravity via an open-loop `mj_rne` feed-forward | **real, but position-only** — no force feedback |
| Grasp | a pre-declared MuJoCo `weld` equality toggled active at pickup (`primitives.grasp()`); a documented "magnetic" stand-in. The gripper DOF (`a7`) exists but is excluded from IK and unused for grasping | **stand-in**, not a gripper |
| Peg-in-hole | a scripted descent (−1.4 mm / control cycle, 6-DoF IK with live xy re-centring, stop at 18 mm depth) guarded by a **joint-torque watchdog**: the sum of \|`actuatorfrc`\| over the 8 right-arm servos, tripping at baseline + 25 N·m (`sequencer.py`) | **scripted trajectory + real contact + threshold guard** |
| Contact | the work-cell scene runs on the collision model with contacts **enabled** — a real peg cylinder, a square pocket, table friction — so the peg↔pocket reaction is genuine MuJoCo physics, and that reaction is what loads the servos the watchdog reads. (The control/ACT scene disables contacts because the raw meshes self-jam at the shoulders.) | **real contact, but not force-regulated** |
| Force sensing | **none at the wrist.** No MuJoCo `touch` / `force` / `torque` sensor anywhere. "Force" is either the servo-effort sum (the watchdog) or a software 3-DoF TCP-force *estimate* from joint torques in the cockpit (`F = (J·Jᵀ)⁻¹·J·τ`, position-only) | **estimate, not measurement** |
| Compliance | **none on the arms** — pure position servos. The only admittance-like code is a 1-D load-equaliser in the dual-carry demo; the cockpit's contact reflex *latches a soft-stop* (it stops, it does not yield) | **absent** |
| Collision geometry | primitive capsules (boxes via `--boxes`) fitted per link; used for **both** self-collision **and** environment/object contact; plus a stricter pre-send kinematic guard in the cockpit | real, reused for cell contact |

**Honest one-liner:** today's *force-guarding* is a joint-torque threshold on a scripted motion, not force control; *grasping* is a weld, not a gripper. That is a legitimate v1 for a sim-first demonstrator — but it is exactly the gap between "assembles a peg when perfectly aligned in sim" and "does compliant, contact-rich assembly."

## 2 · The target

A manipulation core that **(1) measures** the contact wrench at the wrist, **(2) regulates** it — compliant / hybrid position–force control — instead of thresholding it, and **(3) grasps** with a real actuated gripper. Everything below is sim-first; each phase names its hardware boundary explicitly, and each ships with a verification metric in the repo (matching the project's existing test/eval culture).

## 3 · Phased plan

### M1 — Wrist force/torque sensing in sim  *(foundation, low-risk)*
- **Status — shipped.** The `force`+`torque` sensors are in `make_control_model.py` (inherited by the collision + cell scenes) and validated by `sim/test_ft_sensor.py` (both wrists read a known static load to < 0.05 N / N·m; run in CI). The wrench is now the control signal for M2's force-regulated insertion below — which supersedes the "re-express the guard as a threshold" idea with true force *regulation*.
- **Status — on the wire and in the cockpit.** `sim_endpoint` streams both wrist wrenches as telemetry **id 6** (`skate_ros2.protocol.WRENCH_ID`), and the cockpit's force overlay draws the *measured* wrench per arm — magnitude in N, the moment in N·m, labelled `F/T` — instead of the joint-torque estimate. Three things about that path are deliberate. **(1)** Discovery is tolerant: a control MJCF built before M1 simply has no sensors, so id 6 is never sent, and a client must treat its absence as normal rather than as a fault — which is exactly the real Skate's case. **(2)** The payload is a plain nested dict of floats, not a new class. dicts, floats and lists are pickle *primitives*, so a wrench packet resolves **zero globals** through the wire's restricted unpickler: streaming it widens the attack surface by nothing, and `shared_classes_def.py` stays a faithful mirror of the firmware's CAN messages rather than gaining a message the robot cannot send. **(3)** The streamed value is pinned to the sensor reading *bit-for-bit* and again physically (< 0.05 N under known loads, the same bound `test_ft_sensor.py` asserts), because the failure this guards against — a lost frame rotation or a flipped sign — is invisible to a test that only checks the field is present. `tools/skate_ros2/test/test_wrist_wrench.py`, `test_wire_safe.py` and `tools/skate_commander/test/test_force.py`, all in CI. What did **not** change: the cockpit's *compliant contact reflex* (M3 below) still runs on `_tcp_force`'s joint-torque estimate. Switching a display is additive; switching a control loop is a behaviour change that needs its own tests and its own eval, so it is scoped separately rather than smuggled in here.
- **Either backend can back it — measured, not assumed.** That is the "Sim ↔ hardware" requirement below, answered with numbers. The selection is per arm and tagged in the payload (`src`: `sensor` | `estimate`), so one cell and one bare wrist is a supported configuration and the readout never hides which one you are reading. It matters which one you get. Measured on the *same settled state*, with each backend compared against its own no-load baseline (error = ‖Δ − (−F)‖):

  | applied load (N) | sensor, home | estimate, home | sensor, working | estimate, working |
  |---|---|---|---|---|
  | [0, 0, −10] | 0.000 | **9.699** | 0.000 | 4.170 |
  | [10, 0, 0] | 0.000 | 0.856 | 0.000 | 3.251 |
  | [0, 8, 0] | 0.000 | **26.550** | 0.000 | 1.371 |
  | [5, −5, −5] | 0.000 | 5.772 | 0.000 | 0.760 |

  Left wrist; the right tracks it within ~2 N. At the **home** pose the arm is near-singular (σ_min(J) = 0.0205) and `(J·Jᵀ)⁻¹` amplifies whatever torque noise lands in the collapsing direction: the estimate recovers **0.31 N of a 10 N vertical pull** — a 97 % miss — and **invents 26.5 N of phantom vertical force** under an 8 N *lateral* load. At a well-conditioned **working** pose (σ_min = 0.0770) it is still **0.760–4.262 N** off on 10 N-class loads. The sensor reads all four to 0.000 N at both poses. So the measurement wins wherever it exists and the estimate is the fallback for hardware with no cell — not the reverse — and a compliance loop running on the estimate at a folded pose is a known hazard, not a detail. Reproduce: `python sim/eval_wrench_backends.py --model .../skt_v3 --json sim/eval_data/wrench_backends.json`. **Raw data:** [`sim/eval_data/wrench_backends.json`](../sim/eval_data/wrench_backends.json), pinned to this prose by `sim/test_manipulation_numbers.py` in CI. (The estimate column is the cockpit's own `RobotBridge._tcp_force`, called on the joint arrays the endpoint actually puts on the wire — not a re-implementation of it.)
- **Goal:** a true 6-axis contact wrench at each wrist, replacing the actuator-torque proxy.
- **Do:** add a MuJoCo `force`+`torque` sensor pair on a site at each wrist flange; surface the wrench in the telemetry schema and the cockpit plots; re-express the insertion guard as a *wrench* threshold.
- **Replaces:** the `tau_R()` sum-of-`actuatorfrc` watchdog → a real wrench signal.
- **Unlocks:** all of M2–M4 (you cannot regulate a force you cannot read).
- **Sim ↔ hardware:** the sim sensor is exact; the real Skate needs an actual wrist F/T sensor *or* a joint-torque-based estimator — design the M1 interface so either backs it.
- **Verify:** static-load calibration test (apply a known mass/wrench, sensor vs analytic); confirm the re-expressed guard reproduces today's insertion behaviour.
- **Risk:** MuJoCo sensor frame conventions; add a noise model so the signal stays honest for sim-to-real. **Effort:** small–medium; no new control theory.

### M2 — Force-regulated insertion  *(hybrid position–force)* — **SHIPPED**
- **Status — shipped.** `sim/insertion.py` (`Insertion`) regulates the axial contact force during the descent instead of pushing open-loop until a threshold trips, and searches for the bore under misalignment. Verified by `sim/test_insertion.py` (in CI) and swept by `sim/eval_insertion.py`.
- **How:** axial admittance on an accumulating z-setpoint — `z_cmd += clip(kf·(f_ax − f_target), −vz, vz)` — so the wrist descends while the measured axial force (the M1 wrist wrench) is below `f_target` (3 N) and eases off once it reaches it; the force is *regulated*, not rammed. `lead_cap` bounds how far the setpoint may lead the actual wrist so a stalled peg cannot wind up a large command. A **spiral hole-search** with a *pause-and-seat* state machine recovers misalignment: the wrist xy spirals out from the assumed centre, freezes the instant the peg starts to drop so it can seat, and resumes if it stalls. Gravity feed-forward (`mj_rne`, the `reach()` trick) holds height; a wrench-magnitude abort (`w_abort` = 9 N) is the safety backstop. The controller uses only the wrench + wrist proprioception + the assumed centre — never the live peg pose (the sim peg pose is an oracle used only to *score* the eval).
- **Depends:** M1.
- **Sim ↔ hardware:** the controller is identical in sim and on hardware; only the wrench *source* differs (a real F/T sensor or a joint-torque estimator behind the M1 interface).
- **Verify — misalignment-tolerance curve** (rigid fixture via the `fixture_base` weld, 6 directions/offset): with search, 0 mm **1/1** (a zero offset is a single direction), 2 mm and 4 mm **6/6**, 6 mm 5/6, 8 mm 3/6; **without search the open-loop descent jams almost everywhere (≤1/6)**. Peak axial force 3.3–3.6 N out to 4 mm and ≤4.6 N at the 6–8 mm extremes (target 3, abort 9) — regulated, not rammed. This replaces the old single "5/5 under nominal alignment" with success *vs* initial xy error. A **peg-tilt (θ) tolerance** sweep (`--theta 0,3,6,9,12`) shows initial tilts up to 9.3° are levelled to <2° and seated — the controller holds the target orientation upright (`relock=False`), so the 6-DoF IK rights the peg as it inserts. Reproduce: `python sim/eval_insertion.py --model .../skt_v3 --offsets 0,2,4,6,8 --dirs 6 --no-search-baseline --json sim/eval_data/insertion.json` (and `--theta 0,3,6,9,12 --json sim/eval_data/insertion_theta.json`). **Raw data:** [`sim/eval_data/insertion.json`](../sim/eval_data/insertion.json) · [`insertion_theta.json`](../sim/eval_data/insertion_theta.json) — every figure in this bullet is re-derived from those files by `sim/test_manipulation_numbers.py` in CI, so prose and data cannot drift apart silently.
- **Live cycle — integrated.** The controller now drives S4 of the demonstrator's GRAFCET cycle (`sim/sequencer.py`): the right arm force-regulates the insertion (peak wrench ~2.6 N) while the left keeps holding the base at the meet point (`hold_arms`); the full cycle seats, QC-accepts and places the unit, the peg staying centred in the bore through placement. So the *rendered demo and the cockpit run on M2's force control*, not the old open-loop `tau`-watchdog descent.
- **Also shipped:** a `benchmark.py` `insert_m2` task on the new controller (bimanual, scored on the base-recoil-invariant oracle), the peg-tilt (θ) tolerance above, and the spec's **round chamfered H9 bore** — `make_cell_scene.py --round-bore` generates a faceted-cylinder bore (20 facets, 10.4 mm inradius → ≈0.4 mm radial clearance on the D20 peg) with a wider lead-in mouth. The M2 controller seats in it with **no retuning**: misalignment sweep (search on) 0 mm 1/1, 2 mm 4/4, 4 mm 4/4, 6 mm 3/4, peak axial force ≤5.4 N — locked in by `test_round_bore_seats` in CI (generated to a *side* model so the square v1 pocket stays the default and the other tests' shared staging is untouched). So the earlier "small remaining" gap is closed; M2 is complete. **Risk (addressed):** contact stiffness (`solref`/`solimp`) tuning — the rigid `fixture_base` weld keeps the sweep deterministic. **Effort:** medium; core contact-control work.

### M3 — Cartesian compliant (admittance/impedance) arm control — **SHIPPED**
- **Status — shipped.** `sim/admittance.py` (`Admittance`) wraps the position servos in a task-space admittance loop at the TCP: the arm *yields* to an external contact wrench at a tunable per-axis stiffness instead of holding rigid or latching the cockpit's soft-stop — a general controller, not the 1-D dual-carry heuristic. Verified by `sim/test_admittance.py` (in CI) and swept by `sim/eval_admittance.py`.
- **How:** a diagonal virtual mass-spring-damper per world axis — `Mv·e'' + D·e' + K·e = F_ext` — driven by the M1 wrist wrench (baselined at start, so it responds to the *change* — real contact — not the static grasp load / sensor bias). The compliant displacement `e` is added to the nominal TCP pose and realised by the existing 6-DoF DLS-IK on the position actuators (qpos is never written directly); `D` defaults to critical (ζ = 1) so the yield is smooth and returns without overshoot. Steady state `e = F_ext/K`: a low-K axis yields, a high-K axis holds. Gravity feed-forward (`mj_rne`, qvel zeroed → no Coriolis) holds height, as in `reach`/M2. Orientation is held (translational compliance; rotational is a later extension).
- **Depends:** M1; benefits from M2.
- **Sim ↔ hardware:** admittance-on-position-servos ports cleanly to a real position-controlled arm (which the Skate is); only the wrench *source* differs (a real F/T sensor or a joint-torque estimator behind the M1 interface).
- **Verify — commanded-stiffness curve + push-and-yield.** Driven by a supplied wrench (the control law in isolation), the TCP yield settles to `e = F/K` across a 16× stiffness sweep — K = 200/400/800/1600/3200 N/m → 40/20/10/5/2.5 mm at F = 8 N, `e·K = 8.0 N` at every point — and a per-axis K = [400, 1600, 400] gives e = [20, 5, 0] mm (compliant x/z yield, stiff y holds), returning to ~0 when the wrench is removed. A **push-and-yield** with a *real* force on the wrist read back through the M1 sensor (+8 N) yields the TCP ~21 mm along the pushed axis and returns to the nominal pose on release (sensor-in-the-loop). Reproduce: `python sim/eval_admittance.py --model .../skt_v3 --json sim/eval_data/admittance.json`. **Raw data:** [`sim/eval_data/admittance.json`](../sim/eval_data/admittance.json), pinned to this prose by `sim/test_manipulation_numbers.py` in CI.
- **Risk (addressed):** admittance stability vs the inner position-loop bandwidth — symplectic integration + critical damping + the gravity feed-forward keep it stable across the whole sweep. **Also shipped — bimanual compliant carry** (`sim/carry.py` `CompliantCarry`, `sim/test_carry.py`): the object-level generalisation of demo_dual_carry's 1-D tanh load-equaliser — both arms hold a shared bar and one Cartesian admittance at the object frame (driven by the *summed* wrist wrenches, whose internal squeeze cancels; an equal offset to both wrists preserves the closed kinematic loop) yields the whole assembly to a disturbance and returns it. A 10 N push yields the object ~20 mm along the pushed axis and it springs back, the bar never dropped. **Also in the cockpit:** `RobotBridge` gains a selectable contact response — `set_contact_mode("stop"|"compliant")` — where *compliant* yields the TCP via the same admittance law (inlined, driven by the cockpit's existing `_tcp_force` joint-torque estimate) instead of latching the soft-stop; the default stays `stop`, so the existing reflex and its e2e guard are byte-for-byte unchanged (`tools/skate_commander/test/test_compliant.py`). **Also shipped — the operator's toggle, which completes M3.** The mode is reachable from the cockpit instead of only from Python: a `contact_mode` WS command routes to `set_contact_mode`, an **ON CONTACT · Stop / Comply** segmented control sits under *Contact sens.* in the MOTION TUNING popover, and a **COMPLY** chip stands in the status cluster for as long as the mode is engaged — a response that *suspends* the soft-stop latch may not be invisible, and the chip is itself the way back to Stop. Four properties are pinned rather than assumed (10 tests in `test_compliant.py`): the mode may only be entered **by name** — a junk, null or missing `mode` changes nothing in either direction and does not raise, because one bad frame must not take the socket down with it; the snapshot's `contact.mode` is part of the contract, since it is the only thing the chip and the segment paint from; engaging *comply* does **not** clear a stop already latched — the toggle is not a hidden Resume, the same rule OBSERVE follows by landing every transition in E-STOP; and leaving *comply* while the arm is yielded drops the admittance state **without unwinding it**, so the switch can never command a jump back into whatever the arm is leaning on. **Effort:** medium; the main new control theory.

### M4 — Real grasp model  *(actuated gripper)* — **SHIPPED**
- **Status — gripper shipped (opt-in, self-contained).** `sim/make_gripper_scene.py` builds `skt_v3_gripper.xml` — an actuated parallel-jaw gripper (two pads on coupled prismatic joints, a force/motor actuator, real friction, a pad touch sensor) grasping a rectangular part — and `sim/gripper.py` (`Gripper`) does **closed-loop grasp-force control**: `close_to_force` regulates the *measured* pad force (not the raw motor command) to a target. Verified by `sim/test_gripper.py` (in CI) and `sim/eval_gripper.py`: (1) the measured grasp tracks the target across 2–5 N (2 N→2.00, 5 N→5.00, monotone); (2) once the temporary world-pin is released the part is held by **friction alone — no weld** (dz ≈ −3 mm, grasp force persists at target); and (3) a **grasp-slip curve** — a firmer grasp holds a larger downward payload before the part slips out (grasp 2/3/4/5 N → slips at 3.75/4.25/5.00/5.25 N), the expected friction-proportional relationship (flat pad-on-face contact makes the hold scale; the earlier rigid-cylinder stand-in *ejected* instead of slipping — MuJoCo's stiff friction-grasp frontier). Reproduce: `python sim/eval_gripper.py --model .../skt_v3 --json sim/eval_data/gripper.json`. **Raw data:** [`sim/eval_data/gripper.json`](../sim/eval_data/gripper.json), pinned to this prose by `sim/test_manipulation_numbers.py` in CI. The scene is self-contained (no robot meshes), so the arm's control/collision/cell models and all their tests stay untouched.
- **Status — arm integration shipped (grasp → carry → place).** `sim/make_gripper_cell.py` mounts the parallel jaws on the **right wrist** (an opt-in `skt_v3_gripcell.xml`, separate from the default cell model so every other test is untouched), and `sim/gripper_arm.py` grasps a part to a target force and moves it weld-free: with the world-pin released the part stays fixed in the wrist frame through the motion (drift ≈ 5 mm, grasp held ~5 N). `grasp_carry_place` takes it to a full **pick-and-place** — carry the part over a bin, descend, and open the jaws to release it *onto* the bin (the part settles on the bin, `placed` ✓) — held by the gripper's **friction, not the weld** stand-in throughout. Verified by `sim/test_gripper_arm.py` (in CI: both the carry and the pick-and-place). This is the weld-free replacement for `primitives.grasp()`'s magnetic weld, on the actual arm. **Optional follow-up:** the cockpit's point-cloud grasp synthesiser (which needs the oriented IK M2/M3 already use).
- **Status — live demonstrator cycle shipped, weld-free on both hands.** `make_cell_scene.py --gripper` writes an opt-in `skt_v3_cell_gripper.xml` — the same work cell with those jaws on **both** wrists — and `sim/sequencer.py` *detects* them per wrist (`Cell.jaws` / `Cell.jawsL` are `grip`/`gripL`-actuator lookups, not flags or env vars) and runs the whole S0–S7 GRAFCET on them with **no `weld` active anywhere in the cycle** (`test_cell_gripper.py` samples both equalities three times across the cycle — while the left hand is holding, after it has set the base down and let go, and after it has binned the finished unit — and asserts neither ever engages). It is a *different cycle*, not a re-skin, because jaws cannot do the one thing the weld was quietly doing: hold the base in mid-air for free while the peg goes in. So the left hand **picks the base off the table** (S1, 12.00 N measured on its own pad sensor), sets it down on an assembly station and **opens** (S2); the right hand grips the peg (S1, jaw travel +6.19 mm, `grasp_right` inactive), carries and aligns it on friction alone (**0.42 mm** drift in the jaw frame), S4 force-regulates the insert to **22.11 mm** at **2.98 N** peak and then **releases by opening** (jaw travel −12.12 mm, pad force back to 0 N); the left hand then **re-grips the assembled unit** (S5, **0.43 mm** drift) to carry it back to the pose the QC cameras are calibrated for, and lets go of it over the accept bin (S6) before S7 homes. Final unit: depth **22.12 mm**, tilt **1.90°**, alignment error **1.24 mm** — ACCEPT. Full cycle **75.84 s** against the weld path's 42.58 s; `sim/test_cell_gripper.py` (in CI) itemises that +33.3 s step by step (S5 alone is +15.5 s — the re-grip a weld gets for nothing) and holds the takt at 85 s. Four real grip/release operations on the left hand, two on the right, and the peg is never teleported. Both hands run the same closing regulator on a **12 N** target and the two pads do *not* read alike, which is contact geometry rather than a tuning miss: the left hand on the base's flat walls settles at **12.000 ± 0.001 N**, while a cylinder held in a V has two line contacts and the right pad *rings* **10.54–13.37 N** about the same target for as long as the loop runs — so the exit test is a rolling-40 mean (within 0.25 N of target from cycle 71, worst residual 0.196 N over the remaining 329) and not an instantaneous sample, which never accumulates. Quoting one snapshot off that ring would be quoting noise; the number that is stable is the target the mean holds.
- **What the conversion cost — the camera QC gate, measured.** What the conversion took away first was the **fixture camera pair** — the one every published QC number on this page was measured through — and that loss was recorded before it was repaired, not quietly skipped: with jaws on both hands the fixture verdict is **REJECT**, and the reason is the conversion itself. The left tool has to approach the base **top-down** (the pocket faces up, and the base's 60 mm length exceeds the 41.61 mm tip gap, so the approach orientation is forced), which parks the left wrist directly between `qc_top` and the unit at exactly the pose QC inspects. Rendering the real pipeline at its calibration resolution (960×720) at that instant, inside the 300 px inspection ROI `qc.measure()` actually analyses: the weld path shows **1116 peg px** and **7581 pocket-rim px** → `peg_present` true, align 3.40 mm, depth 19.02 mm → **ACCEPT**; the jaw path shows **0 peg px** and **827 rim px** — **89 % of the rim gone** → `peg_present` false → `align_err_mm` None → **REJECT**. Same probe, same `qc.py`, same masks, same renderer on both paths, so the REJECT is caused by the conversion and not by the measurement ([the two ROIs side by side](img/qc_occlusion_jaws.png)) — and the two cells settle the part **7.74 mm** apart, *16 px of that 300 px window*, published rather than rounded away precisely so the reader can rule out subject motion for themselves instead of taking "same probe" on trust. Reproduce: `MUJOCO_GL=egl python sim/eval_qc_occlusion.py --model .../skt_v3 --json sim/eval_data/qc_occlusion.json`. **Raw data:** [`sim/eval_data/qc_occlusion.json`](../sim/eval_data/qc_occlusion.json), pinned to this prose by `sim/test_manipulation_numbers.py` in CI — including the part the negative result turns on: the **pose oracle accepts both paths** on the same seated unit (22.12 mm / 1.90° / 1.24 mm), so what the conversion cost is the *sight* of the part, not the assembly. Stated plainly: **the last weld was the one holding the part in the overhead camera's line of sight.** That measurement stands unchanged and the committed fixture-pair numbers stay on the weld path where they were earned; what the conversion cost was scoped as real work rather than papered over — in-situ inspection optics aimed at the assembly station, a second camera pair and not a re-tune — and the bullet below is that work, done.
- **The gate, restored — a second pair, in situ.** `qc.measure()` now takes a `CameraPair` instead of two hard-coded camera names, and the scene carries a second one: `qc_station_side`, the same lens at the same standoff and field of view as `qc_side`, aimed at the assembly station instead of the QC fixture. It is read in the one instant the weld-free cycle *has* and a welded cell structurally cannot: S5 retracts the right wrist 85 mm and parks it **before** the left hand re-grips, so for that moment the finished unit stands free on the station with both hands off it — a cell with a weld in it never lets go of the part except *onto* the weld, which is why this gate is a property of the conversion and not a patch bolted on after it. Through the same masks, the same inspection ROI and the same `qc.measure()`, the station pair shows **956 peg px** and **5788 rim px** → `peg_present` true, **alignment 1.12 mm and depth 17.80 mm** → **ACCEPT**, and the pose oracle agrees on that same frame. So the weld-free cell is camera-gated on its own cell; `Cell.qc_gate` records which pair decided (`fixture` on the weld path, `station` on the weld-free one) and the event stream carries both. One consequence is a check rather than a claim: with the camera agreeing, S6 no longer takes the reject detour, so the camera-gated eval lands on exactly the takt `sim/test_cell_gripper.py` measures off the oracle with no renderer attached at all — two gates that share no code, one reads pixels and the other reads the simulator's own pose, and one number to a hundredth. If the station pair ever stops seeing the part, that equality is the assert that goes red.
- **What did *not* change — and the one thing that did.** The default `skt_v3_cell.xml` gains **exactly one line**, the `qc_station_side` `<camera .../>`, because both scenes come out of one builder. It is therefore **no longer byte-identical** to the file M4 shipped, and retiring that word costs less than keeping a claim that has quietly stopped being true. What byte-identity was standing in for is checked directly instead, and that holds: a camera carries no dynamics, so generating the default cell from the previous and the current `make_cell_scene.py` and stepping both under the same non-trivial control input leaves every model size equal — same bodies, geoms, joints, equalities, sensors, actuators, `nq` and `nv` — and leaves `qpos` and `qvel` **bit-identical**, the largest difference at any step exactly zero rather than merely small. One thing *does* move, and it is worth naming here rather than leaving to be discovered: camera **numbering**. The station lens lands third, right behind the fixture pair, so the four view cameras each shift up one id. Nothing in the tree picks a camera by number — every selection is `camera="name"`, and the single place that handles an id resolves it *from* a name — so the shift has nothing to break; it is still a fact about the file, and facts about the file go in the file's paragraph. The structural half of that is held in CI by `sim/test_manipulation_numbers.py`, in the job that has no MuJoCo to load a model with: strike the camera line out of `SCENE_HEAD` and not a trace of the station is left behind, and the struck line is a `<camera>` with no body, geom, joint, weld or site riding in with it. So every existing demo, log, benchmark and test stays on the weld path and both the published 42.6 s reference cycle (`logs/cycle_001.json`, oracle-gated) and the separate camera-QC run that ACCEPTs on that path (`logs/cycle_002_camera_qc.json`) still reproduce exactly. Three consequences of the gripper scene are worth stating rather than glossing: **(1)** it needs `<option impratio="10" cone="elliptic">` — with MuJoCo's default pyramidal friction cone the clamped peg creeps ~12 mm out of the jaws during the S3 align — and `<option>` is *model-wide*; the shipped default model keeps MuJoCo's default cone, but the two scenes are therefore not physics-identical and their cycle times are not a controller comparison. **(2)** The camera's depth estimate reads ~3.4 mm **low** against the sim oracle at this lift height (2.2 mm at 0.140, 5.5 mm at 0.160 across the lift sweep), so the QC verdict was always calibrated to the part presentation, not an absolute depth gauge. **(3)** With a friction grasp a *stalled* insert heals itself the moment the jaws open — the peg drops the last millimetres under its own weight — so an after-the-fact camera check cannot see the stall, and S4's in-loop `seated` flag is the only honest stall detector; `test_cell_gripper.py` asserts on `seated` for exactly that reason. On the weld-free cell (3) is no longer a caveat but the whole gate, which is the second reason the oracle path is the honest one to ship.
- **Goal:** replace the weld stand-in with an actuated parallel-jaw gripper closing on friction contacts, with grasp-force control. (The spec's round chamfered H9 bore is already in the tree from M2 — `make_cell_scene.py --round-bore`, verified by `test_round_bore_seats` — so M4 is now purely the gripper.)
- **Do:** model jaws as contacting geoms driven by the (originally decorative) `a7` gripper DOF ✓; grasp-force target via the wrench or a tendon ✓; wire the cockpit's point-cloud grasp synthesiser (`grasp.py`, already real and unit-tested) to *execute* — **still open**, and it is the last piece of M4. The oriented IK it was waiting on has since shipped on both sides: sim-side `primitives.Arm.ik_step6` is what the whole manipulation core runs on, and cockpit-side `Kinematics.ik_step(..., target_R=)` plus `set_ik_target(arm, pos, rot=)` let the drag-gizmo command wrist orientation (`rot=None` keeps the classic free-wrist position-only solve). What is left is the synthesiser→executor path itself, not a solver.
- **Depends:** M1 (grasp force); oriented IK — **shipped**, sim (`ik_step6`) and cockpit (`ik_step(target_R=)`) both.
- **Sim ↔ hardware:** the real Skate gripper geometry is unknown until hardware — build M4's interface to swap geometry, mirroring how the weld stand-in is already documented as replaceable.
- **Verify:** grasp a part by friction and carry it through the full cycle *without the weld*; a grasp-slip curve (payload until slip vs grasp force).
- **Risk:** friction-grasp stability in MuJoCo (notoriously stiff); jaw/part contact tuning; IK reach under orientation constraints. **Effort:** medium–large; the most sim-tuning-heavy phase.

### M5 — Hardware bring-up  *(Phase 2, on the real Skate)*
- **Goal:** the sim controllers run on the physical arm.
- **Do:** source the wrist wrench on hardware (real F/T sensor or joint-torque estimator behind the M1 interface); re-tune admittance gains to the real dynamics; calibrate; re-run the misalignment-tolerance and grasp-slip metrics on hardware.
- **Depends:** M1–M4 and the Skate arriving.
- **Honest boundary:** everything above is sim-only until then. The sim-to-real gap (contact stiffness, sensor noise, latency) is exactly what M1's noise model and the prior SO-101 real-hardware bring-up experience are meant to de-risk.

## 4 · Sequencing & the smallest useful slice

M1 was the keystone — low-risk, and nothing regulates force without it. The smallest end-to-end slice that actually moves the review needle is **M1 + M2**, and it is now **delivered**: a *force-regulated* insertion reported with a *misalignment-tolerance curve*, replacing the scripted-push-plus-threshold. That result converts "assembles when perfectly aligned" into "assembles under realistic misalignment via contact force" — the real manipulation claim. **M3 has since broadened it** from insertion to a general Cartesian *compliant* controller (yield at a commanded per-axis stiffness, `sim/admittance.py`), and **M4 adds the real grasp** — an actuated gripper with grasp-force control that grasps and carries a part *weld-free* on the arm, and that now drives **both hands of the demonstrator's own S0–S7 cycle** on an opt-in scene with no `weld` active in it anywhere (left picks the base off the table → right grips the peg → force-regulated insert → both open to release → left re-grips the unit and bins it; 22.12 mm at 1.90° tilt, 75.84 s against the weld path's 42.58 s). That conversion also produced the cleanest negative result in the project: the cell passes on the sim oracle but its **camera** gate now REJECTs, because the top-down left tool occludes `qc_top` at the verify pose — the last weld was the one holding the part in the overhead camera's line of sight. Only the M5 hardware bring-up (waiting on the physical Skate) remains.

## 5 · Honesty rules

M1, M2, M3 and M4 are all in the tree with their tests — M4 being the actuated gripper (grasp-force control + a friction grasp + a grasp-slip curve, a weld-free grasp-and-carry on the arm, and the live S0–S7 cycle running **both** hands on those jaws; `sim/test_gripper.py` + `sim/test_gripper_arm.py` + `sim/test_cell_gripper.py`); **only M5, the hardware bring-up, is still a plan, not implementation.** Two boundaries have to be said every time the weld-free cycle is claimed, because both are easy to leave out and both change what the claim means: it runs on a **separate opt-in model** (the default cell — the one every other demo, log and benchmark uses — keeps its welds, and the one line the station lens added to it is a camera, which changes no size and no state), and it is camera-gated on a **second pair**, not the fixture pair the published QC numbers were measured on — that pair is still occluded at this cycle's verify pose (measured: 0 peg pixels in the inspection window against 1116 on the weld path), still read, and still logged, because the gate was restored by adding optics rather than by walking the finding back. "Weld-free" and "camera-verified" are true of this project on the same cell only in that sense, and neither sentence should be allowed to borrow the other's evidence. This doc keeps SkateArm's honesty rules: each phase states its sim-vs-hardware boundary, ships with a verification test that lands in the repo, and claims nothing until its metric is committed. Nothing not yet in the tree with its test should be described as done, in progress, or working — and everything here is sim-only until the M5 hardware bring-up.
